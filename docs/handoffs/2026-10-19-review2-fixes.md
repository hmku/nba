# Handoff 2026-10-19 - review2 fixes: REST lost responses, publish policy, hash parity, intel privacy (cloud session)

## What was accomplished
1. **REST retries vs non-idempotent writes** (`db/rest.py`, `ops/rest_ledger.py`).
   - `RestClient.request` retries GETs, and writes the caller marks `idempotent=True` (the bulk upsert and
     insert-ignore in `publish --rest`), on any transport error or 5xx. A POST, PATCH or DELETE is retried
     only on `ConnectError`/`ConnectTimeout`, when the request never left. A read timeout, a dropped
     connection, or a 502/504 after sending raises the new `RestOutcomeUnknownError` (`rest_outcome_unknown`,
     a subclass of `RestUnreachableError`). Any other 5xx is returned unretried.
   - `RestStore.insert` handles a lost response by re-reading the row by its generated primary key and
     accepting it if it holds our values. `RestStore.patch` and `delete` re-issue the request once, which is
     safe because each one is a CAS or sets absolute values. On a 0-row match, `_transition`, `end_run` and
     `tasks.done` re-read the row and accept it only if it holds *our* write: same status and values, plus
     the exact `updated_at`/`ended_at` we sent. A genuine repeat call therefore still fails as before.
   - `plan()`: a lost insert response continues with our own txn, so add_drop still gets its approval.
   - Both reviewer repros now succeed: `mark_submitted` with a lost PATCH response, and `plan(add_drop)` with a
     lost POST response. New tests use the fake PostgREST with injected `ReadTimeout`s, both after the write
     committed and before it: `tests/test_rest_ledger.py`, "lost responses" section.
2. **SQL publish and sqldump now apply `publish_policy`** (`ops/status.publish`, `db/sqldump.py`): `merge`
   tables are upserted, `insert` tables use `ON CONFLICT DO NOTHING`, `locks` are skipped. The result now
   includes `policy` and `inserted`. New tests in `tests/test_db_schema_publish.py` show that a stale local
   `pending` approval does not overwrite `rejected` in the target (SQLite→SQLite), for both paths. The
   runbook (`docs/runbooks/agent_ops.md` §5/5b) and the sqldump docstring are updated.
3. **Python/TS canonical-JSON parity** (`ops/intel.canonical_json`, `web/src/lib/agentPure.canonicalJson`).
   - Numbers are printed the way JS prints them on both sides, via `js_number`: `1.0`→`1`, `-0.0`→`0`,
     `1e-07`→`1e-7`.
   - Integral values beyond ±(2^53−1) and non-finite numbers are rejected on both sides.
     `validateSnapshot` turns that into a 400-style validation error.
   - Python sorts keys by UTF-16 code units, and lone surrogates are escaped like `JSON.stringify` does.
   - A new shared fixture, `tests/fixtures/canonical_json_parity.json`, is generated by
     `tests/test_canonical_json_parity.py` (which also checks hand-written expectations) and checked by
     `web/tests/intel.test.mjs`. The existing vector's hash is unchanged.

## Decisions & rationale
- Lost write responses are resolved by re-reading, never by a blind resend. The one re-issue (PATCH/DELETE)
  is safe because every PATCH/DELETE in rest_ledger is conditional or absolute.
- Integers beyond 2^53 are rejected rather than stringified. JS has already lost precision after
  `JSON.parse`, so nothing could hash them consistently.
- With the unlock, the activity page uses the service client for every read, so the run timeline also
  shows chat events.
